## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| section DB JSON (vendored/static) → lookup | The bundled JSON is third-party MIT data; names/points are treated as untrusted display + geometry input |
| section name from parsed model → sectionDb | `model.sections` keys come from attacker-controlled `.std` files and become DB lookup keys |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | prototype pollution | mitigate | sections.json stored as a positional ARRAY; sectionDb indexes into a `Map` at first use — no plain-object keyed by untrusted name (a `.std` naming a section `__proto__` cannot pollute) |
| T-02-02 | DoS | geometry cache size | mitigate | cache keyed per distinct section label (bounded by distinct `model.sections` keys, not per member); dispose contract owned by 02-04 SceneBuilder |
| T-02-03 | Tampering | vendored DB integrity | mitigate | provenance + MIT license header pins source/commit; validation at vendor time (≥1,000 entries, meters, CCW); worst case a corrupted entry renders garbage geometry, never executes |
| T-02-04 | Tampering | XSS via section names | mitigate | names flow into three geometry only (never rendered as HTML); any text display (02-06 StatsSummary) renders via React text nodes — never dangerouslySetInnerHTML |
| T-02-05 | DoS | hostile polygon size | mitigate | points bounded by the DB schema (fixed small outlines); nearestShape uses fixed constant polygons; no unbounded polygon construction from names |
| T-02-SC | Tampering | npm installs | mitigate | No new installs in this plan (02-02 owns the 3D-stack checkpoint; three/vitest already installed there) |
